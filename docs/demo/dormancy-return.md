# 휴면 복귀 재생

`RETURN_FROM_DORMANCY`는 합성 앱 미방문 구간을 별도 사건과 원본 결과로 기록한다. 승인된 계획의 1~3주 휴면 가정에 따라 마지막 앱 활동과 복귀 사이를 7일 이상 21일 이하로 검사한다. `priorDormancyEventId`는 해당 학생의 마지막 앱 활동 사건을 가리킨다. 현재 계약에는 별도 DORMANCY_START 사건이 없으므로, 이 참조를 휴면 직전 활동의 기준점으로 해석한다. 이 해석은 생성기에도 동일하게 적용해야 한다.

가입 JOIN은 최초 활동 기준점으로 사용할 수 있다. 반환한 학생이 다시 휴면하는 경우 이전 RETURN_FROM_DORMANCY도 활동 기준점이다. 거부되거나 실패한 앱 요청도 방문 시도로 세므로 그 사이의 앱 활동을 숨길 수 없다. 지급·카드 구매는 앱 밖에서도 발생할 수 있어 미방문 구간을 끊지 않는다. 기간 마감과 INFLUENCED_DECISION 주석도 방문으로 세지 않는다. 다른 학생의 활동은 무관하다. 동일 시각의 명령은 sequence 순서로 판별하며 기간 길이는 UTC Instant의 Duration으로 계산한다. 경계 직전/직후 마이크로초는 포함 범위를 벗어나면 거부한다.

타인 참조, 없는 참조, 미래 sequence, 누락된 원인 연결, 수동 지급을 기준점으로 삼는 경우와 중간 앱 활동을 거부한다. timeline 입구에서 먼저 검사하고 실제 dispatcher에서는 기준점의 실행 결과도 대조한다. 복귀 결과는 기준점·종류·실제 성공/거절/실패 상태·휴면 시작 시각·복귀 시각·기간을 보존한다. 최종 검증은 명령과 실제 결과에서 주석을 다시 구성하여 원본 결과가 바뀌지 않았는지 확인한다.

재생은 membership·계좌·현금·위시·관계·행동 행을 변경하지 않는다. 같은 event ID와 같은 입력의 중복 실행은 기존 dispatcher 결과를 반환한다. 입력 충돌은 거부한다. 원본 결과는 raw index에 기록하고 논리 projection에도 유지한다. 일반 bootJar에 simulation 클래스는 포함되지 않는다.

검증은 단위 경계/참조/원본 변조 사례와 실제 PostgreSQL 38개 테이블의 복귀 전후 동일성, 중복 실행, 복귀 후 실제 CREATE/DEPOSIT, replay journal 원본·정규화 결과 대조를 포함한다. 정확한 명령·테스트 수·파일 해시는 `verification-b78043.json`에 기록한다.

이는 입력 사건 목록에서 검증한 합성 앱 미방문 주장이다. 실제 사용자의 미방문을 입증하거나 가입 상태를 휴면으로 바꾸는 기능이 아니다. 데이터 생성기의 성향·주별 방문 빈도·100명 전체 cutoff/모든 휴면 구간 검증은 아직 수행하지 않았다. 기간 마감, adjustment/correction 명령, 실제 Python 추천·리캡, 전체 데이터 생성/CSV·재현성, selective apply/restore·대표 UI·Owner 콘솔 보존·현재 demo 적용도 남아 있다. 승인된 OpenAPI와 dataset schema bytes는 변경하지 않았다.
