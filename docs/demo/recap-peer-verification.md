# 리캡 또래 비교와 대표 위시 원본 대조

액션 `act-c2b82bf7b19c285fb1f796650ffb9019`은 CLOSE_WEEK/CLOSE_MONTH에서 실제 Python 호출 전에 `SimulationRecapPeerVerifier`를 실행한다. 기존 snapshot 생성기나 metric helper를 기대값 계산에 호출하지 않는다. 같은 종료 시각의 PostgreSQL 원본 계좌·학생·학원 자격·위시·대표 선택·원장·효과 행을 읽고, `period-source.json`의 `peer_source`에 저장한 뒤 검증한다. DB는 실행기가 만든 일회용 로컬 DB이다.

본인의 대표 위시는 명시적 선택을 우선하고, 선택이 없으면 삭제되지 않은 IN_PROGRESS 위시를 생성 시각·UUID 순으로 선택한다. 입력 대표 ID가 원본 선택과 같은지 확인한다. 또래는 본인을 제외한 같은 학원, 활성 계좌 및 탈퇴하지 않은 회원, PROVIDED 나이, 본인 나이 ±2 범위로 한정한다. 본인 나이가 PROVIDED가 아니면 또래 배열은 비어야 한다. 친구 관계와 위시 공유 범위는 이 익명 집계의 추가 자격 조건으로 사용하지 않는다.

52주 구간의 실제 원장과 정정 체인을 합산하여 양의 입금·이체 유입이 발생한 서울 기준 월요일 주의 개수를 계산한다. 0회인 적격 또래도 배열에 포함한다. 대표 위시가 있는 또래만 목표액 대비 생애 배분액의 백분율을 계산하며, 목표 초과 달성률을 100%로 잘라내지 않는다. 52주 이전 저축은 활동 주 수에 포함하지 않지만 달성률에는 반영한다. 원장 발생 시각이 종료 경계 이상이거나 정정 원본이 없으면 검증을 거부한다.

원본 계좌 UUID의 PostgreSQL 순서로 배열을 비교하여 현재 실제 요청의 원소 순서·개수·값까지 확인한다. 이것만으로 여러 또래의 UUID 순서가 서로 다른 독립 DB 간 canonical 재현성을 해결하지는 않는다. 익명 배열 정규화와 전체 100명 이력 재현성은 별도 검증이 필요하다.

`event-N-period-verification.json`은 이번 실행부터 `period`와 `peers` 객체를 포함한다. `period`는 기존 본인 기간 검사 결과이며, `peers`에는 대상 또래 수, 달성률 수, 본인 대표 위시 UUID가 들어간다. 두 검사가 모두 통과했을 때만 파일을 생성하고 Python을 호출한다. 실패 전에 생성한 snapshot과 원본 파일은 남기며, 검증 실패를 무효과로 보고하지 않는다. 원본 journal은 기존 방식대로 파일 바이트와 checksum을 보존한다. 제품 HTTP/OpenAPI와 canonical dataset schema는 변경하지 않았다.

회귀는 나이 범위 양끝, 탈퇴·닫힌 계좌·불명 나이 제외, 무활동 포함, 대표 없는 달성률 제외, 원소 누락·변조, 타인 대표 선택, 경계 정정, 끊어진 정정, 52주 경계와 100% 초과 달성률을 검사한다. 실제 PostgreSQL/Python 리캡 테스트에서는 같은 학원 또래가 기존 서비스로 2,500원을 10,000원 목표 위시에 저축하고, 주간·월간 요청의 25% 달성률을 원본에서 대조한다. 정확한 실행 결과는 `verification-c2b82.json`을 따른다.

성공 story 후보의 완전성·권한, Python의 전체 결과 독립 재계산, ADJUST/CORRECT 실행 명령, 전체 canonical bundle/CSV, 100명 전체 행동·실제 추천 Python, selective apply/restore, 대표 UI, 최신 Owner 콘솔 보존과 현재 demo 적용은 여전히 미완료다. 이번 액션에서 원격 쓰기, commit, Feature Run 또는 액션 상태 변경은 수행하지 않는다.
