# Feed local feature provenance

The approved wire contract is `api/openapi.yaml#/x-feed-ranking-v1`. This document records local feature implementation; the public feed orchestration and durable continuation are still pending.

`FeedCategoryClassifier` evaluates a checked-in portable TF-IDF vocabulary, IDF and category-weight artifact in-process. The source is the controller-created paired `crabit-data` checkout at `02c704d2967c6c9ec042f7b33b36172c10e2c2b4`, specifically `wish_category_classifier.py`. The artifact records that source revision and source-file SHA-256. The wire classifier version is `wish-category-v1@sha256:` followed by the SHA-256 of the exact UTF-8 resource bytes, including the final newline. Enabled settings reject a configured digest that differs from the bundled artifact.

The artifact preserves ordered categories, lowercase preprocessing, Unicode word-boundary character 2–3 grams, smoothed IDF, cosine normalization, earliest-category ties, threshold 0.05 and fallback `기타`. No title is sent to the ranking service. `FeedTitleSimilarity` implements Python's directional `SequenceMatcher(None, left, right).ratio()` using Unicode code points, earliest-match ties and the default autojunk rule for the second sequence at 200 or more characters.

Generate the two JSON documents with `scripts/recommendation/export-feed-classifier.py <paired-data-worktree>`. The exporter checks the exact Git revision and clean classifier source, uses the original Python classifier, prints an artifact and an independent oracle, and does not modify either repository. Persist the returned artifact under `src/main/resources/recommendation/feed-classifier-v1.json` and the oracle under `src/test/resources/recommendation/feed-feature-oracle.json`. The existing corpus covers 406 category examples and 207 title-similarity pairs, including all category keywords, mixed words, random strings, empty titles, Unicode whitespace, emoji, asymmetric matches and autojunk boundaries.

`FeedRankingDeadline.start()` begins one monotonic 500ms budget before candidate/metric preparation. The HTTP client accepts the same deadline; its Supplier overload starts that budget before running preparation. Exhausted preparation produces no HTTP call. Serialization, transport, response read and validation consume the remainder; late results are discarded. The caller must still ensure no transaction spans the network call when wiring the public feed.

`RecapAuthorMetrics` is the shared account-wide calculator extracted without changing recap output. `FeedMonthMetricsService` chooses the previous calendar month in Asia/Seoul, proves full account/behavior observation before calculating complete values, and emits null values for PARTIAL/UNOBSERVED months. It uses the existing effective ledger correction chains and raw outgoing visit semantics, including signed savings, distinct deposit days, population standard deviation of gaps, first/second-half pace, abandonment and transfer counts. It does not restrict transactions to visible cards. The legacy behavior retention's five-minute future-clock allowance is conservatively included in the full-observation boundary.

V20 adds a deployment-time history baseline and transactionally recorded `[valid_from, valid_to)` versions of Wish, Shared Card, account, membership, directional follow and bilateral block rows. Source changes use PostgreSQL time and monotonically increasing version identities. Migration baseline creation takes source-table locks; it does not interpret predeployment business timestamps as proof of earlier observed state. Local fixture TRUNCATE clears the matching history and starts a fresh coverage boundary.

`FeedVisitEvidenceService` runs inside first PROFILE_VISIT acceptance. It takes source-table SHARE locks in the order membership, account, card, block, follow, Wish, waits for existing source mutations, rechecks current profile access and reads database capture time. It never takes account/relationship advisory locks or source-row locks. This makes capture coherent with committed source history. These broad locks require contention and compound-mutation lock-order review before release; the focused concurrency test covers an in-flight Wish update, not every lifecycle interleaving.

Historical categories use all visit-time shared, undeleted, eligible cards, including published ABANDONMENT cards. Current ranking candidate state filtering is a separate concern. Accepted evidence contains category IDs and opaque history version references, never raw titles; historical local source versions retain the original fields needed to classify a delayed visit. A complete empty set is `COMPLETE []`; prebaseline or future occurrence produces permanently `UNKNOWN null`. Previously accepted events migrate to `UNKNOWN/LEGACY`. Exact replay preserves the original evidence even after title change or unsharing, and database updates to evidence are rejected.

PROFILE_VISIT event identity and evidence remain through the inclusive later of received-time plus 90 days and occurred-time plus 90 days. Cleanup deletes strictly after that endpoint. FEED_CLICK/FEED_EXPOSURE retain their existing received-time expiration. The scheduled evidence cleanup is bounded to the same batch sizes as behavior cleanup. Historical source-version compaction is not implemented yet.

Remaining integration work includes durable five-minute continuation and replay, final projection/privacy locking, GET/POST metadata and result-position wiring, visit-signal consumption, actual Java→Python integration, deployment documentation and registered verification script. Local feature tests do not establish those behaviors or any controller gate.
